# Security and architecture review — August 2026

A full review of the implementation across three questions: is it secured, is it
well architected, and are the chosen components the right ones. Conducted before
the Debian box existed, against the dev stack running on macOS.

Every finding below has a status: **fixed**, **accepted** (a real risk, decided
against fixing, with the reason), or **deferred** (needs the target box or a
decision that has not been made). Findings are cross-referenced to the decision
they produced in [`decisions.md`](decisions.md).

Where a claim is marked *verified*, it was tested against a running stack, not
inferred from configuration.

> **Read as a dated record.** This is what the review found in August 2026 and
> is deliberately not edited as the repo moves on. Three things below have since
> changed and are left as written:
>
> - the macOS dev stack and `dev-testing.md` were deleted (D8, D9)
> - Tailscale was replaced by a self-hosted `wg-easy` tunnel, so `tailscale0`
>   is now `wg0` and S7's socket finding is moot twice over (D26)
> - the media disk is a temporary 2 TB, not the 8 TB assumed here (D27)
>
> The findings themselves stand; only the names have moved.

---

## Summary

The build was in better shape than a static read suggests, and worse in one
specific way than any file in it recorded.

Better: the `/data:/data` invariant is enforced by a mechanical assertion rather
than a comment, the hardlink test genuinely spans two containers, the compose
layering fails in the safe direction, and `decisions.md` is a real ADR log. All
eight apps did in fact enforce authentication when probed.

Worse: almost none of that authentication was established or checked by the
repo — it was set by hand, once, and nothing would have noticed it changing. Two
of the load-bearing claims in the documentation were false: that UFW protected
the service ports, and that authentication was "enabled in every app" as a
property of the build rather than of one afternoon's clicking.

The largest finding is not a vulnerability. It is that the security posture was
**asserted in prose and nowhere else**. Most of the work below converts those
assertions into things that fail loudly.

## What was verified, not assumed

Probed against the running stack before changing anything:

| Service | State found |
|---|---|
| Sonarr / Radarr / Prowlarr | `forms`, `authenticationRequired: enabled`, password set |
| qBittorrent | unauth API → 403; CSRF on; `bypass_local_auth` false |
| SABnzbd | login enforced, `inet_exposure = 0`, password set |
| Bazarr | `auth.type: form`, password set |
| Jellyfin | `StartupWizardCompleted: true`, unauth `/Users` → 401 |
| Jellyseerr | `initialized: true` |

So `README.md`'s "authentication is enabled in every app" was true. It was just
not true *because of anything in the repo* — the *arr logins were configured by
hand during setup, which is exactly the situation the rest of this document is
about.

## Security findings

### S1 — `BIND_ADDR` failed open · **fixed** (D20)

`docker-compose.yml` used `${BIND_ADDR:-0.0.0.0}` on ten published ports.
Deleting the variable from `.env` published the whole stack on every interface,
silently. The same file already had the correct pattern one service away, in
`${CADDY_BIND_ADDR:?...}`.

Now `${BIND_ADDR:?}`. There is no default, so the decision has to be made
explicitly and a missing value stops the stack instead of opening it.

### S2 — The bootstrap window was unguarded · **fixed, except two wizards** (D18)

Between `docker compose up -d` on a fresh box and a human finishing each
first-run wizard, the stack served open setup screens on the LAN. Whoever
reaches Jellyfin's wizard first becomes its administrator — and Jellyseerr
authenticates against Jellyfin, so that is the household front door too.

Mostly closed. The *arrs now come up with authentication already required (S3),
and `provision.sh` sets the credentials for the *arrs, qBittorrent, SABnzbd and
Bazarr before anyone logs in.

**Jellyfin and Jellyseerr cannot be closed from configuration** — neither
exposes a pre-authentication bootstrap path. The README now sequences around
that instead: bring the stack up on `BIND_ADDR=127.0.0.1`, finish those two
wizards over an SSH tunnel, run `audit-auth.sh`, and only then widen to the LAN.

### S3 — *arr authentication was manual, and one toggle removes it · **fixed** (D18)

The `forms` auth on Sonarr, Radarr and Prowlarr was set by hand. Nothing in the
repo established it and nothing re-asserted it.

The sharper half is what happens afterwards. The *arrs offer
`AuthenticationRequired = DisabledForLocalAddresses`, which is common forum
advice and is specifically wrong in this stack: Caddy reaches the backends over
the compose bridge, so **every proxied request carries a private source
address**. Setting it makes the tailnet-facing admin UIs anonymous-admin while
remote access keeps working perfectly, which is the worst possible failure
signature.

*Verified in both directions.* With `DisabledForLocalAddresses`, `GET /` returns
`200` with no login. Caddy's own access log confirms the mechanism — proxied
requests arrive with `"remote_ip": "172.23.0.1"`.

Fixed in two halves, because the two settings live in different places:

- **Method and scope** are config-file elements, so they map onto the same
  `SONARR__AUTH__*` mechanism already used for the API key. They are pinned in
  `docker-compose.yml` and re-applied on **every container start**, so an
  accidental change reverts on restart rather than persisting.
- **Credentials** live in the app database, not `config.xml`, so `provision.sh`
  sets them over `PUT /api/vN/config/host`. This works before any UI login
  exists only because the API key is pinned ahead of first start — the payoff
  D12 was buying and had not been used for.

*Verified on a fresh container:* with the env vars pinned and no credentials
set, `GET /` redirects to `/login`, empty credentials are rejected, and
`/loginsetup` is unreachable. The PUT then returns 202 and the credentials take.

A useful side-finding: the *arrs apply environment configuration at runtime
**without writing it to `config.xml`**, so the file disagrees with the running
app. Anything auditing these settings must ask the API. `audit-auth.sh` does.

### S4 — UFW does not filter Docker-published ports · **fixed** (D19)

The stated boundary was "no router port forwarding, plus UFW denying inbound"
(D1, spec §5.3, CLAUDE.md invariant 4). The second half was never true.

Docker publishes ports by DNAT in `nat/PREROUTING`; the traffic then traverses
`FORWARD`, never `INPUT`, which is the chain UFW filters. Every service in this
stack was reachable from any attached network while `ufw status` reported a
default-deny firewall. Nothing in the repo touched `DOCKER-USER`.

`setup.sh` now appends a guarded block to `/etc/ufw/after.rules` populating the
`DOCKER-USER` chain — which Docker leaves empty and evaluates first, precisely
for this — returning established traffic, loopback, `tailscale0` and
`$LAN_SUBNET`, and dropping the rest.

This does not change the threat model; it makes the existing one true. The
absence of a port forward becomes the second line of defence rather than the
only one.

**Skipped when `LAN_SUBNET` is unset**, with a warning, because applying it
without one would cut the LAN off from Jellyfin and break Infuse on the Apple
TV. Note that the working `.env` on the dev box has no `LAN_SUBNET` line at all.

Written here, verifiable only on the target — see `verification.md` item 7a.

### S5 — SSH was the weakest host surface · **fixed**

`ufw allow OpenSSH` was unsourced, accepting SSH from anywhere the host could be
reached, and `ufw allow from $LAN_SUBNET` was not port-scoped. No key-only auth,
no `PermitRootLogin no`, no fail2ban. `unattended-upgrades` is required by spec
§2 and was never implemented.

`setup.sh` now scopes SSH to `$LAN_SUBNET` (tailnet SSH is already covered by
the `tailscale0` rule), installs and enables fail2ban, and configures
unattended-upgrades for security updates only with **automatic reboots off** — a
reboot mid-import is worse than a delayed patch on a LAN-only box.

`PasswordAuthentication no` is applied **only if an `authorized_keys` file
already exists**. Otherwise it writes `PermitRootLogin no`, warns loudly, and
tells you to install a key and re-run. Locking the operator out of a headless
box in another room is a worse outcome than password auth surviving one more
day.

### S6 — `.env` was world-readable · **fixed**

Mode `0644`, holding every password in the stack plus the Eweka Usenet account
and both indexer API keys. Neither `setup.sh` nor `provision.sh --init-keys`
narrowed it. `setup.sh` also sources it **as root**, so a writable `.env` is
arbitrary root execution.

Both now `chmod 600` it, and `validate.sh` asserts the mode.

### S7 — `tailscaled.sock` is mounted into a root Caddy · **accepted** (D21)

The socket is the tailnet control API, not a cert-issuing endpoint, and Caddy in
`caddy:alpine` runs as root — so a Caddy compromise reaches the tailnet, not
just the proxy. `:ro` on a socket restricts nothing.

Accepted rather than fixed: both alternatives (non-root Caddy with
`TS_PERMIT_CERT_UID`, or host-issued certs mounted read-only with no socket at
all) need a real tailnet to validate, and there isn't one. Written down in D21
with the preferred option so it is revisited when Q1 and Q2 close, rather than
being rediscovered.

### S8 — Caddy had no access logging · **fixed**

Nine two-line site blocks, no `log` directive anywhere. Caddy is the only remote
entry point and none of the apps behind it record who reached them, so there was
no way to answer "has anyone else touched this box" — ever.

Every site now imports a shared snippet with a rolled JSON access log, plus
`X-Content-Type-Options`, `Referrer-Policy` and `-Server`. HSTS is in the
production Caddyfile only: on `localhost` it would pin every `*.localhost` host
to HTTPS in the browser for a year and break unrelated local work. No CSP — the
*arr UIs, Jellyfin's web client and Jellyseerr all rely on inline scripts.

The snippet is defined per-environment in the two Caddyfiles rather than in the
shared `sites.caddy`, which keeps routing shared and environment differences
where they already lived.

### S9 — No container hardening · **fixed**

No `security_opt`, no log rotation, no healthchecks. Unbounded `json-file`
logging on the same 500 GB SSD as the OS and every app database is a slow way to
take the stack down.

Added `no-new-privileges:true` and 10 MB × 3 log rotation to every service, via
YAML anchors. `cap_drop: ALL` is not viable — the LinuxServer images start as
root to drop to `PUID`/`PGID` — but `no-new-privileges` blocks escalation after
that drop, which is the part that matters. *Verified:* all ten containers start
and reach healthy with it applied.

### S10 — Secrets are passed as environment variables · **accepted**

Visible to anything that can run `docker inspect` or read `/proc/<pid>/environ`.
Acceptable on a single-admin box where the only account that can do either is
the one that owns the secrets anyway. The LinuxServer images support a `FILE__`
prefix if this ever needs tightening.

### S10b — The audit read whole config files, and one check was a false pass · **fixed**

`audit-auth.sh`'s first version read all of `sabnzbd.ini` and all of Bazarr's
`config.yaml` into shell variables, then picked fields out of them. Both files
contain third-party account credentials — the Usenet provider under
`[servers]`, and the subtitle providers in Bazarr's config — so an
authentication audit was holding secrets it had no use for. That is how the
Usenet username in S11 below reached a terminal.

Both now slice the section they need **inside the container**, so the provider
sections never cross the boundary at all. Narrowing the read is a stronger
guarantee than masking the output, because it does not depend on remembering to
mask.

The same bug had a second and worse consequence. `grep -qE '^password = .+'`
over the whole `sabnzbd.ini` matches the *provider's* password as readily as
SABnzbd's own, and `.ini` files repeat key names across sections. So with an
empty web UI password and a configured news server, the check reported
**"SABnzbd: a password is set"** — a false pass on the control that matters
most, since SABnzbd runs post-processing scripts. *Verified against a synthetic
config:* the old expression passes, the section-anchored one correctly fails.

Worth generalising: an assertion that reads more than it needs is not just a
disclosure risk, it is a correctness risk, because the extra data can satisfy
the assertion.

### S11 — Three API keys were exposed during this review · **action for the operator**

`SONARR_API_KEY`, `RADARR_API_KEY` and `PROWLARR_API_KEY` were printed to a
terminal while probing the live stack, and Bazarr's API key and password hash
appeared in a container read. These are dev-box values on a loopback-bound
stack, but the same `.env` is intended for production.

Rotating is cheap — delete those lines from `.env`, re-run
`./scripts/provision.sh --init-keys`, then `docker compose up -d` and
`./scripts/provision.sh`.

**Doing it exposed a second problem, since fixed.** Prowlarr's application links
and Jellyseerr's Radarr/Sonarr connections each store their own *copy* of the
app's API key, and `provision.sh` skipped both when the link already existed. So
rotating a key left four stale copies behind, and the failure is silent: indexers
stop syncing and requests stop reaching the *arrs, with no error anywhere
obvious. "Rotate your keys" was advice that broke the stack.

Both now compare the stored key against `.env` and `PUT` an update when they
differ. Jellyseerr's `PUT` also needs `id` stripped from the body — the `GET`
returns it and the `PUT` rejects it with a 400.

`--init-keys` also now fills an existing blank assignment in place instead of
appending a second one. Appending works, since later assignments win for both
`source` and Compose, but a few rotations in it leaves the same key defined
several times.

*Verified after rotation:* both Prowlarr application links and both Jellyseerr
connections pass their live test endpoints, Recyclarr syncs both instances, and
`audit-auth.sh` confirms each app answers to the new key and rejects a bogus one.

## Architecture findings

### A1 — `setup.sh` had never run to completion · **fixed**

Found while testing the new steps. `preflight()` ended with:

```bash
$DRY_RUN && warn "DRY RUN — nothing will be modified"
```

When `DRY_RUN` is false that returns 1, and under `set -e` a non-zero return
from a top-level function call exits the script. **Every non-dry-run invocation
exited silently immediately after preflight, having done nothing** — exit code 1,
no error message.

It survived because the only documented way to exercise the script is
`--dry-run`, which is the one path where the bug cannot fire. On the target it
would have looked like a successful, instant, completely inert run.

This is the clearest argument in the review for testing the path you will
actually use. `dev-testing.md` now documents a non-dry-run container recipe.

### A2 — `docs/spec.md` was stale, and `CLAUDE.md` made it authoritative · **fixed**

The spec never mentioned Usenet, SABnzbd, Jellyseerr, Recyclarr or
`/data/usenet/`. Its §4 table listed 8 services against a 10-service stack, and
its §3.1 tree omitted the Usenet trees. Meanwhile `CLAUDE.md` said "if anything
here disagrees with the spec, the spec wins" — pointing at a document that
predated half the build. That is an instruction to regress the implementation.

The spec was brought up to date rather than demoted: §4's table and the
dual-protocol rationale, §3.1's tree, §5.2's routes and access logging, §5.3's
security constraints, and two new §9.1 acceptance criteria.

### A3 — No backups of anything · **fixed** (D22)

`${CONFIG_ROOT}` holds every app database — watch history, requests, quality
profiles, indexer setup, user accounts. The media is re-acquirable; that is not.
`grep -r backup scripts/ setup.sh` returned nothing. D7 said to back it up before
pulling images and provided no means to, which combined badly with `:latest` on
every image: the update path was *pull an unpinned major version over unbacked-up
state*.

`scripts/backup-config.sh` triggers each *arr's own backup command first — they
checkpoint SQLite properly, and copying a live database yields a file that
restores cleanly and is subtly corrupt — then tars `${CONFIG_ROOT}` to
`/mnt/disk1/backups` with retention. `setup.sh` installs a daily timer with
`RequiresMountsFor`, so a missing mount stops the unit rather than filling the
SSD with what is meant to be the off-SSD copy.

*Verified:* archive, retention (5 → keep 2), and a byte-identical restore.

One disk is not an offsite backup. It covers the SSD dying and a bad image pull,
which are the two failures that actually happen.

### A4 — No healthchecks; `depends_on` was start-order only · **fixed**

Caddy started before its backends were listening, so the first minute after a
reboot served 502s. Recyclarr could fire its sync against an unready Sonarr and
then wait a full day for the next `@daily` run.

Every service now has a healthcheck, and Caddy, Jellyseerr and Recyclarr use
`condition: service_healthy`. *Verified:* the whole stack comes up in dependency
order with all ten reaching healthy.

### A5 — `provision.sh` hardcoded the download client hosts · **fixed** (D19/§7)

`host: "qbittorrent"` was a literal. On VPN day qBittorrent moves to
`network_mode: service:gluetun` and loses its own network identity — the *arrs
must then reach it at `gluetun:8080`. The download client would have stopped
working with no error that pointed at the cause.

Now `${QBIT_HOST:-qbittorrent}` and `${SAB_HOST:-sabnzbd}`, documented in
`.env.example` as the thing to change when the VPN lands.

### A6 — Recyclarr was an undocumented prerequisite · **fixed**

`provision.sh` links Jellyseerr to Radarr and Sonarr by quality-profile *name*
(`UHD-2160p`, `WEB-1080p`), and those profiles only exist after a
Recyclarr sync. Recyclarr runs `@daily`, and the README's command block never ran
one — so a first-run `provision.sh` silently took the warn-and-return path and
left Jellyseerr unwired.

`docker compose exec recyclarr recyclarr sync` is now in the README sequence,
before `provision.sh`, with the reason.

### A7 — Doc drift · **fixed**

`CLAUDE.md` and `dev-testing.md` both said "exactly the five media services"
where `validate.sh` asserts six. Corrected, along with the repo-layout tables in
both files.

### A8 — bash 3.2 on the dev box · **noted, one bug fixed**

macOS ships bash 3.2, the target has bash 5. `mapfile`, `declare -A` and safe
empty-array expansion under `set -u` are unavailable here. The first draft of
`backup-config.sh` used `mapfile` and its retention silently did nothing — it
kept four backups with `BACKUP_KEEP=2`. Rewritten with the read-loop idiom
`validate.sh` already used, and the constraint is now documented in
`dev-testing.md`.

## What is well built

Stated plainly, because it is most of the repo and none of it needed changing:

- **The `/data:/data` invariant is enforced mechanically.** `validate.sh` asserts
  the exact service set, a single shared mount source, and no remapped container
  paths. This is the number-one silent failure in this class of build, and it is
  checked rather than commented.
- **`test-hardlinks.sh` genuinely spans two containers**, and D9's choice of a
  named volume on macOS — rather than a bind mount, whose inode semantics would
  make the test meaningless — shows it was designed to be able to fail.
- **Production-as-default compose layering.** Forgetting the override on Debian
  yields a correct stack; forgetting it on the Mac fails loudly. That asymmetry
  is the right way round and the reasoning is written down (D8).
- **The qBittorrent RCE vector was already closed** — `autorun_enabled: false`
  and an empty `autorun_program`, per spec §5.3 — and CSRF was deliberately kept
  on while only host-header validation was disabled (D13). A considered trade,
  not a blanket disable.
- **API-driven idempotent provisioning** rather than shipping pre-baked
  `config.xml` files.
- **`decisions.md` as an ADR log**, and `verification.md` distinguishing verified
  from assumed. Rare, and the reason this review could focus on substance rather
  than reconstructing intent.

## Component choices

| Component | Verdict |
|---|---|
| **qBittorrent** | **Keep.** Best free torrent client for *arr integration; categories and API are first-class. Deluge is stagnant; Transmission is weaker on categories. |
| **SABnzbd** | **Keep.** NZBGet is lighter, but on an i7-8700K with 32 GB that advantage is irrelevant, and SABnzbd has the more continuous community and better *arr defaults. |
| **Both, Usenet at priority 1** | **Correct.** D14's reasoning holds. Usenet wins on speed, retention and no seeding obligation; anime coverage on Usenet is genuinely poor, so the torrent side is not redundant. |
| **Prowlarr** | **Correct.** Jackett is legacy; app-sync is why indexers are never configured per-app. |
| **Jellyfin + Jellyseerr** | **Correct.** Jellyseerr as the front door means nobody but the administrator sees an *arr UI (D16). |
| **Recyclarr** | **Keep.** `sqp-streaming` on Radarr is a good call for a single 8 TB disk — roughly 15–30 GB a film rather than 60–90. |
| **Caddy** | **Keep.** The tailscaled cert integration is the reason, and it is worth the socket caveat in S7. |
| **Indexers** | **Changed** — see below. |
| **VPN** | **Deferred, and the largest remaining risk** — see below. |

### Indexers — the one component gap · **fixed** (D23)

The four defaults were `Nyaa.si`, `SubsPlease`, `AnimeTosho` and
`Tokyo Toshokan`. All four are anime. The torrent side therefore covered *only*
anime, and every TV and film search depended entirely on the Eweka and NZBgeek
subscriptions staying live — with no fallback for a lapsed subscription, or for
older and obscure titles that have aged out of Usenet retention.

Added `The Pirate Bay` and `YTS`, both *verified* against Prowlarr's live
connectivity test. Dropped `Tokyo Toshokan`, which indexes substantially the
same sources as Nyaa.

`1337x` — the best of the general-purpose public trackers — was tried and left
out. Prowlarr rejects it on save: *"Unable to access 1337x.to, blocked by
CloudFlare Protection."* Using it needs a FlareSolverr container and a matching
Prowlarr indexer proxy, which is an always-on headless Chrome, so it is
documented in `.env.example` as opt-in rather than shipped.

Worth noting what that failure demonstrates: Prowlarr validates every indexer at
save time, so a definition that cannot be reached fails during provisioning
rather than becoming an indexer that silently returns no results months later.
That behaviour was already relied on in `provision.sh`'s comments; this is the
first time it has actually fired.

### A note on Quick Sync

Worth recording so expectations are right: **Infuse direct-plays**. The Apple TV
path — which is the primary playback path — will rarely invoke Jellyfin's
transcoder at all. The Quick Sync work matters for other clients and for remote
streaming over Tailscale, not for the main use case. It is still worth having;
it is just not what makes the Apple TV work.

## Deferred: the VPN

Gluetun remains commented out (spec §7), and this is now the largest open risk in
the build. qBittorrent seeds to public trackers from the residential IP, and the
indexer change above increases torrent usage rather than reducing it.

The deciding feature is port forwarding — without it, inbound peers fail and
seeding degrades badly. Mullvad and IVPN have both dropped it. Candidates remain
Proton VPN Plus (NAT-PMP, which Gluetun can use to configure qBittorrent's
listening port automatically), AirVPN and PIA.

When it lands, three things matter:

1. Set `QBIT_HOST=gluetun` in `.env` and re-run `provision.sh` (A5).
2. Verify the kill switch — qBittorrent must have no route out if the tunnel
   drops. Gluetun's firewall does this by default; confirm it rather than
   assuming it.
3. `validate.sh` asserts Gluetun stays commented out. That assertion is the
   reminder, and it should be updated deliberately, not deleted in passing.

## Still untested

Unchanged from the standing position, plus what this review added. None of these
could be checked off the target, and none should be reported as working until
`verification.md` says otherwise:

hardware transcoding · `*.ts.net` certificates · tailnet-only binding · the UFW
and `DOCKER-USER` rules taking effect · fail2ban · unattended-upgrades · the
backup timer firing · smartd alert delivery · unattended boot after power loss.

The `DOCKER-USER` rules are the one to be most careful about. They are *written*
and their idempotency is proven, but a rule that is written and never loaded
protects nothing. `verification.md` item 7a checks the chain is populated and
then port-scans the WAN IP from off-network.
